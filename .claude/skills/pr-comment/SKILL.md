# PR Comment

Write a short, readable GitHub PR comment from what actually changed. Output is markdown the user pastes into GitHub.

## 1. Find the changes

Work from the diff, not from memory of the conversation.

```bash
git status --short                      # staged, unstaged, untracked
git diff HEAD --stat                    # staged + unstaged vs HEAD
git diff HEAD                           # read the real changes
```

- **Tree is clean?** The work is already committed. Use the commits on the branch:
  `git log <base>..HEAD --format='%h %s'`, then `git show --stat <sha>` for the latest one(s).
  If it is unclear which commits belong in the comment, ask once; do not guess.
  `<base>` is the repo's main branch (`main` here); confirm with `git branch -vv` if unsure.
- **Skip noise:** `*.pyc`, `__pycache__`, `target/`, `node_modules/`, lockfiles, build output,
  generated files. Don't list them and don't describe them.
- Untracked files count: `git status --short` shows them, `git diff` does not. Read them directly.

## 2. Work out the why

For each change, find the reason in this order: the user's request in this conversation, commit
messages, a nearby spec or plan (`docs/superpowers/specs`, `docs/superpowers/plans`), then the code.
If the reason is not discoverable, leave it out rather than invent one.

## 3. Work out how to test it

Only list the layers the change touches. Take commands from the repo, never from habit:

- Frontend: scripts in `frontend/package.json` (`test:unit`, `test:integration`, `test:contract`, `build`).
- Spring Boot: `./mvnw test` in `backend/spring-boot`.
- FastAPI services: `pytest tests/unit` and `pytest tests/` in each `backend/fastapi-*`.
- E2E: Playwright in `e2e/` (`npx playwright test`, needs the full stack running; see `RUNNING.md`).
- Check what CI runs (`.github/workflows/ci-*.yml`, `e2e.yml`) if a command is in doubt.

**Be honest about coverage.** If no automated e2e test covers the change (check `e2e/tests`, and note
`describe.skip`), say so and give short manual steps instead. Never imply a test exists that doesn't.

**Results:** include a "Last local run" line only with numbers you got from running the commands in
this session. Otherwise leave it out. Never write "all tests pass" without having run them.

## 4. Write it

Keep it short: it is read at a glance in a PR.

```markdown
## Summary
<1-3 sentences: the problem, and what this PR does about it.>

## Changes
**<Area>**
- <What changed, and why when it isn't obvious.>

## Testing
**Unit**
<commands>

**Integration**
<commands, plus what they cover>

**E2E**
<command, or manual steps when nothing automated covers it>

## Notes
- <Only if relevant: migrations, new env vars/secrets, deploy order, known risks or follow-ups.>
```

Rules:
- Group changes by area; one line per change. Merge trivial ones. No file-by-file listing.
- Say **why** in the same bullet as the **what**. Don't add a separate "motivation" essay.
- Name new env vars, migrations, endpoints and flags exactly as they appear in code.
- Put commands in fenced blocks, one per layer. Manual steps are a short numbered list.
- Omit empty sections (for example Notes). Skip layers the change doesn't touch.
- **No attribution or "generated by" text of any kind**, no co-author lines, no tool footers.
- No emoji, no marketing tone, no restating the diff line by line.

## 5. Deliver

- Show the markdown in a fenced block (use four backticks if it contains code fences) so it can be copied.
- Save it to the session scratchpad if one is listed, otherwise don't write a file. Never put it in the
  repo working tree where it could be committed by accident.
- Do **not** post it with `gh pr comment`, and never commit or push. Posting is outward-facing; offer it,
  and only do it if the user asks.
